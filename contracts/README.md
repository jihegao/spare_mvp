# Contract Bundle

This directory is the first Contract Curator Agent deliverable for the contract-first backend migration.

The files here are draft JSON Schema contracts for the application-facing boundary:

- `project.schema.json`: editable Project JSON owned by the frontend modeling workflow.
- `aircraft_support_v1_project.schema.json`: strict clean Project JSON boundary for `aircraft_support_v1` Scenario compilation; it white-lists model-facing authoring roots and excludes UI draft state, runtime config, validation diagnostics, RMS allocation process records, and run/result artifacts.
- `scenario.schema.json`: compiled Scenario JSON owned by the Simulation Adapter.
- `run.schema.json`: persisted run lifecycle record.
- `result.schema.json`: metrics and summary returned from a Mesa-backed run.
- `artifact_manifest.schema.json`: versioned index of run artifacts.
- `visualization_state_series.schema.json`: M9.1 offline visualization replay frames, event references, and run/result/artifact traceability; M9.2 online `state_frame` SSE events reuse the same frame fields.
- `scenario_adapter_mapping.json`: evaluator-visible mapping from compiled Scenario JSON input fields to Mesa constructor inputs.
- `rms_allocation_plan.schema.json`: versioned local RMS allocation plan boundary for a selected basic mission, equipment mission reliability `R(T)`, equipment MTTR, allocation method, and algorithm version. Basic missions come only from Project `basicMissions[]`; their duration is derived read-only and recorded in the result input snapshot, while composite/periodic mission profiles and node-exposure fields are outside this contract.
- `rms_allocation_result.schema.json`: versioned recursive RMS result boundary for the selected aircraft/basic-mission input snapshot, node parent relationship, installation count, running ratio, local/cumulative allocation shares, allocated metrics, verification status, warnings, and assumptions. The same boundary supports XLSX import preview, editable results, explicit save, restore, and export.
- `modeling_import.schema.json`: M5 first-slice modeling data import and validation boundary for draft/published lifecycle, object collections, field-level validation issues, and run-reference overwrite protection.

These schemas are not a replacement for the Mesa model or Claude-governed simulation semantics. They define the application data boundary that backend, database, frontend integration, and evaluator agents can consume. The earlier project ontology contract has been removed from active schema/runtime/test scope.

The current frontend Project JSON is the raw `defaultScenario` shape from `front/sim-engine.mjs`; `schema_version` and `project_id` may be supplied later by an application envelope but are not required inside that raw payload. RMS workbench plan/result envelopes may be persisted after an explicit result save so the page can restore the selected basic mission, editable recursive result, and its context, but remain process records rather than formal model inputs.

Basic support activity CSV is an input adapter to the existing Project contract, not a new persisted schema or root. Its canonical columns and compatibility aliases are documented in `../docs/basic-support-activity-csv-import-design.md`. Import rows stage definitions into top-level `supportActivityJobs[]`; `supportActivities[]` remains the plan/reference layer with `activityCodes[]` and `predecessors`. The #307 CSV contract does not add maintenance-method or replacement-ratio columns because those are host-plan fields, not reusable job fields. `activityCode` is a Project-global key: batch/existing duplicates and unknown, cross-host, cross-type, ambiguous, self, or cyclic predecessor references fail the entire batch before the Project draft is dirtied. Successful imports use the existing Project save path; validation failures schedule no save.

The persisted/backend Project JSON boundary is narrower than the in-browser draft. `front/api-client.mjs` and `src/spare_mvp_backend/project_payload.py` strip fields that are UI draft, legacy preview, runtime config, helper dictionary, or misspelled non-model data before Project persistence or Mesa compilation: `missionProfile.profileType`, `missionProfile.endCondition`, `missionProfile.repeatCycleHours`, `missionProfile.analysisRequests`, `supportResourceOverrides`, `deletedSupportResourceKeys`, `modelingDictionaries`, `modelingImportValidation.validationLevel`, `supportResources[].equipment`, `supportResources[].equipmentId`, literal `supportActivities[].requireDevices`, `supportActivities[].requiredDevices`, `supportActivities[].requiredPersonnel`, `supportActivities[].resourceId`, `supportActivities[].planGroupId`, and support-activity rule UI switches/floats such as `supportActivities[].useCalendarRule` and `supportActivities[].calendarDayFloatRatio`. Basic support activity definitions persist in top-level `supportActivityJobs[]`; each `supportActivities[]` row is a plan reference layer with `activityName/activityType/planType`, plan constraints, `activityCodes[]`, and its `predecessors` map, so activity definitions and resource requirements stay in the job/resource tables. Corrective and preventive rows additionally own the canonical pair `maintenanceMethods` / `replacementRatio`; both must be present together, single non-replacement requires 0, single replacement requires 1, and dual selection accepts 0..1. Historical rows missing both materialize as `['non_replacement']` / `0`; scalar `repairType` migrates only from exact `原位维修` or `换件维修`, while unknown or conflicting canonical-plus-legacy input fails closed. `repairTypes` and `components[].specialRepairProfile` ratios are not maintenance decision fallbacks. Persisted `planType` is normalized to one of `使用保障方案`, `修复性维修方案`, `预防性维修方案`, or `后勤保障方案`. `basicMissions[].supportActivityName` is a retained behavior relationship and must uniquely match `supportActivities[].activityName`; `supportActivities[].name` and `id` are not fallback relationship keys. Project-level `analysisRequests` can still feed ExperimentPlan construction, but formal Monte Carlo runtime values belong to `ExperimentPlan.config.analysisRequests.largeSample`, not to the Project model input.

Mission-task field ownership is likewise single-source: `basicMissions[].minRequiredSorties` owns the minimum-equipment authoring value and is only displayed as inherited data in composite task items; `compositeTasks[].priority` owns task priority. New Project/import/export payloads must not write `basicMissions[].priority`, `compositeTasks[].taskItems[].priority`, or `compositeTasks[].taskItems[].minRequiredSystems`. Legacy child-level values are read once during migration, then removed; a conflicting legacy minimum and basic-mission minimum fails closed instead of choosing a value silently. Existing saved Project rows can be migrated with `scripts/migrate-issue-127-mission-task-fields.py`; versioned published imports and historical run/snapshot evidence are intentionally not overwritten and must be republished as a new version.

周期性任务的规划组合以 `missionProfile.periodicProfileLists` 持久化：`month[].weekProfileIds` 固定包含 4 个、最多 5 个字符串坑位，`year[].monthProfileIds` 固定包含 12 个字符串坑位。空字符串是正式的“未配置”值，Project 保存、导出和重新读取均必须原样保留，不能替换成首个可用 ID。Scenario 编译选择最高的已配置层级：年槽存在非空引用时按年展开，否则月槽存在非空引用时按月展开，否则直接使用 `periodicTasks[]` 周剖面；更高层全部为空不阻断短周期任务。非空的悬空周/月引用、周剖面引用不存在的复合任务、复合任务引用不存在的基础任务以及无法生成实例均 fail closed。编译输入在 `mission_profile.periodic_source` 中记录 `level/label/configured_slots`，空槽不产生任务实例且不被默认值替换。

The clean `aircraft_support_v1` exporter adds the stricter model-input gate. `reliabilityBlockDiagram` remains model-facing authoring input, while canvas positions, selection state, and other drawing UI metadata are stripped. Aircraft mission reliability analysis histories are immutable project-level records exposed by their own API and are not written back into Project JSON. RMS allocation draft plans/results may travel with the editable Project payload for page restore, but the clean exporter strips them; validation or verification reports, run results, runtime outputs, and artifact manifests/payloads likewise are not legacy fallback inputs for Project compilation.

Task reliability projections keep the ordered four-field `result_fields` summary and its half-even display values. The summary transport additionally reports `total_samples` and `successful_samples`; `mission_wave_rows` and `series` contain one stable row per successful simulation sample and mission wave, identified by zero-based `sample_index` plus a one-based display label. Page and XLSX detail consumers must preserve these rows and must not aggregate them across samples.

Carry-list projections preserve each row's raw `used_quantity` and `carried_quantity`, where carried quantity is the recommended quantity multiplied by the successful sample count. Overall spare utilization is `sum(used_quantity) / sum(carried_quantity)` over the complete unfiltered row set; consumers must not average row percentages or clamp values above 100%. A complete raw row set whose real total denominator is zero has status `zero_carried` and is rendered as `--` by both the page and XLSX summary. An empty projection or missing/invalid raw quantity has status `data_unavailable` and is rendered as `数据不可用`; consumers must not infer it from aggregate metrics, recommended quantities, or legacy row percentages. Filtering, hiding, and sorting affect detail rows only.

`aircraft_support_v1_project.schema.json` is the clean-Project contract for the current formal model family. It is intentionally stricter than `project.schema.json` and earlier persisted payloads: unknown top-level fields fail closed, component scalar reliability fields are stripped in favor of `failureDistribution`, and UI/runtime/RMS-allocation/run-result roots are not accepted. `modelingImportValidation` is retained as input provenance so reduced-scope imports can carry disabled-domain evidence into Scenario mapping provenance; disabled support domains may therefore have empty `supportNodes` or `supportActivities` arrays, while the Simulation Adapter still fails closed for illegal references or non-disabled missing behavior inputs. It is also intentionally earlier than `aircraft_support_v1_input.schema.json`: Project roots such as `components`, `supportResources`, `supportActivities`, task profiles, hierarchy, and k-out-of-n settings still need the Simulation Adapter to compile them into the model-family input object. `ProjectJsonExporter(target="aircraft_support_v1")` is the run-path boundary for adapter Project input and `runtime_config.projectJson`; it must not be used to bypass Scenario compilation.

For equipment product reliability, `products[]` owns MTBF/MTTR scalar and distribution values. Exact `components[].productId` references receive synchronized compatibility projections because the current Simulation Adapter still consumes component distributions; editing a component table cell must therefore update the product first and refresh every exact reference.

Clean Project golden fixtures live under `tests/fixtures/clean_projects/`. They freeze the minimal contract example, a legacy polluted Project after exporter cleanup, and the full M9.6 platform Project after exporter cleanup. `tests/test_clean_project_golden_fixtures.py` is the drift check: it compares those fixtures to current `ProjectJsonExporter` output, validates them against `aircraft_support_v1_project.schema.json`, blocks known and pattern-matched frontend/runtime marker fields plus separate result/artifact object fields from entering model input, and keeps the public canonical template / M9.6 package / clean Project derivation chain locked.

`modeling_import.schema.json` is an application data-entry contract, not a Scenario contract. It can describe imported Project draft data, object IDs, references, validation issues, and publication lifecycle; final Scenario JSON must still be compiled by the Simulation Adapter.

Canonical Project Excel import is an adapter to `project.schema.json`, not another schema. The `Project` sheet contains `field` and `value` columns for scalar/object roots; array roots use exact Project root names as sheet names and dotted field paths as columns. Object and array cells are JSON. `/api/projects/import-xlsx/preview` performs no write, reuses Project normalization/validation and aircraft-support relationship checks, and reports `sheet`, `row`, `field`, and the precise nested `reference_value`. `/api/projects/import-xlsx/create` is create-only: it validates again, records an audit event, and returns `409 project_already_exists` instead of overwriting an existing ID. Both routes authenticate system/data administrators before reading their larger request envelope; decoded XLSX files are limited to 12 MiB, ZIP expansion and sheet dimensions are bounded, and formula cells are rejected instead of trusting cached values.

`modeling_import.schema.json` also preserves the Phase 2 support-organization/resource and support-activity-library boundaries: recursive support organization nodes, equipment-linked spare rows, personnel specialty values with local dictionary fallback, basic support activity jobs, activity-library references, duration distributions, and predecessor job links.

`scenario.schema.json` requires an explicit `simulation_model` with `family`, `model_id`, and `contract_version`. The active selector and `simulation_inputs` reference accept only `aircraft_support_v1`; retired `smoke` and `aviation_support` selectors and input definitions are not part of the active schema bundle.

The Simulation Adapter lives at `src/spare_mvp_contract/adapter.py`. It validates current Project JSON contract roots, rejects retired `smoke` and `aviation_support` adapter entrypoints with `retired_model_family`, compiles `aircraft_support_v1` for product formal runs, and writes traceable run artifacts. Maintenance plan scope and policy compile to explicit `aircraft_model`, `equipment_id`, `maintenance_methods`, and `replacement_ratio` fields in `aircraft_support_v1_input.schema.json`; mapping provenance records both their Project sources and snake_case targets. M9.7.3 defines the `aircraft_support_v1` formal Monte Carlo/projection path through the current `RunIntent -> /api/runs -> RunService -> SimulationAdapter -> aircraft_support_v1 -> SQLite + artifacts` boundary.

`run.schema.json` repeats `model_family` and `model_id` for query, audit, and Result validation. Active formal runtime records use `aircraft_support_v1` / `AircraftSupportV1Model`; `ScenarioCompilerGate` remains available as the failed compile-gate model id.

`result.schema.json` accepts only `aircraft_support_v1` summaries and requires the current snapshot metric family.

Result fixture metrics are treated as Simulation Adapter normalized summaries derived from `src/spare_mvp_abm/aircraft_support_v1/model.py snapshot()`. The five active contract fixtures form a minimal current Project -> Scenario -> Run -> Result -> ArtifactManifest object chain. `visualization_state().metrics` remains a visualization surface and is not the Result schema source.

The `downtime_factors` user projection deliberately omits fault-mode fields from event details and anomaly snapshots, including nested event payloads. Task and phase context, localized event descriptions, and `DAY_n HH:MM` time labels remain canonical; model-internal events may retain fault mode when simulation algorithms require it.

M9.1 state-series replay is a separate visualization contract. `visualization_state_series.schema.json` requires each frame to carry run identity, typed aggregate state, event summaries, trace fields back to run config/input project/compiled Scenario/result/manifest artifacts, and event entries with `event_id`, `run_id`, `step`, `event_type`, and metric references. For `aircraft_support_v1`, mission rows in each frame also carry the task-planning fields used by the platform mission view: periodic task, composite task, basic task, day index, wave index, required aircraft type/count, duration, and assigned tail numbers. Older state-series artifacts without those mission planning fields must not be inferred from id/name/aircraft_type fallback labels; the mission schedule view should block and require a new formal `aircraft_support_v1` run.

M9.2 online state stream is the run subscription envelope over that same frame contract. `GET /api/runs/{run_id}/state-stream` emits SSE events named `run_status`, `state_frame`, and `artifact_ready`; each `state_frame` carries the same frame shape as `visualization_state_series.frames[]` plus stream metadata such as `stream_id`, `artifact_id`, `frame_index`, and `frame_count`. `artifact_ready` hands the frontend back to canonical `/api/runs/{run_id}/artifacts/{artifact_id}` download and the normal `visualization_state_series` replay parser.

M9.3 run lifecycle/control uses canonical `POST /api/runs/{run_id}/control` rather than changing the state-frame contract. The minimal supported actions are backend-confirmed `cancel` and `retry`; unsupported `pause`, `resume`, `step`, and `reset` fail closed with audit records. Retry-pending runs must not expose stale result or artifact payloads as current official outputs.

M9.4 aviation_support formal execution remains historical context only in archived documentation and the retired model source. It is absent from active schemas, mappings, fixtures, and positive contract tests; negative adapter/formal regressions continue to require `retired_model_family` with replacement `aircraft_support_v1`.

M9.5 aviation_support formal Monte Carlo is likewise archived history rather than an active contract branch. The current canonical Monte Carlo path is `aircraft_support_v1`; `monte_carlo_base` and the four `analysis_projection_*` artifacts derive from the formal run artifact chain rather than frontend demo calculations.

M9.6 freezes the platform case package, field coverage table, and golden fixtures before M9.7 formal aircraft-support model-family work. `tests/fixtures/m9_6_platform_case_export.json` records the deterministic published modeling import -> Project -> ModelingSnapshot -> ExperimentPlan -> RunIntent -> MonteCarloRunConfig -> compiled `aircraft_support_v1` Scenario chain. `tests/fixtures/m9_6_field_coverage.json` classifies every business leaf from the canonical import package as `consumed`, `derived`, `defaulted`, `governance_only`, `ignored`, or `unsupported`; after M9.7.4 the M9.6 frozen-field unsupported summary is 0. `tests/fixtures/m9_6_expected_artifact_kinds.json` freezes the expected single and Monte Carlo artifact kind surface. M9.6 does not make `independent-mesa`, port `8765`, or static HTML output a formal product entry; M9.7 completed the formal `aircraft_support_v1` model family, and M9.8 completed platform embedding plus `independent-mesa` retirement. The retired `independent-mesa/GLM` and `independent-mesa/GPT` source trees are removed from the active repository; historical design notes remain only under `docs/archive/deprecated/superpowers/`.

M9.7.1 adds the `aircraft_support_v1` schema/compiler contract. `contracts/aircraft_support_v1_input.schema.json` owns the model-family input payload, while `contracts/scenario.schema.json` keeps the canonical Scenario envelope and references that independent schema for `model_family = "aircraft_support_v1"` / `model_id = "AircraftSupportV1Model"`. `contracts/run.schema.json` and `contracts/scenario_adapter_mapping.json` expose the same model-family selector and mapping metadata. The compiler gate can compile the M9.6 platform case into an `aircraft_support_v1` Scenario and must fail closed for missing fields or illegal references.

M9.7.2 unlocks the `aircraft_support_v1` single-run contract without claiming final field coverage. `contracts/result.schema.json` accepts `model_family = "aircraft_support_v1"` result summaries, and `SimulationAdapter.run_scenario()` writes the same canonical result, artifact manifest, run chain, metrics/report/log, four single-run projection artifacts, and `visualization_state_series` artifact surface as other formal single runs.

M9.7.3 unlocks `aircraft_support_v1` formal Monte Carlo through `SimulationAdapter.run_monte_carlo_scenario()` and canonical `/api/runs`. The run writes `sample_results`, `aggregate_result`, `monte_carlo_base`, four `analysis_projection_*` artifacts sourced from the base artifact, and a representative-sample `visualization_state_series`; failed samples are isolated in `failed_samples` while aggregate metrics use successful samples only. Formal artifacts/results and lite Mesa responses expose the same `metric_moments` envelope for the seven product-facing metrics: arithmetic mean over each metric's finite native-number samples, unbiased sample variance with denominator `n-1`, explicit `null` variance for `n < 2`, units/variance units, per-metric valid `n`, and total/success/failure counts. The allowlist excludes sample identity, names/status, event/log/debug data and other run metadata; missing values, numeric strings, booleans, NaN and infinities are never zero-filled or coerced into the moments. Finite extreme inputs use scaled statistics; if a variance exceeds the finite JSON-number range, the envelope retains valid `n`, emits `null` plus `invalid_reason=sample_variance_not_finite`, and the UI renders it as unavailable instead of Infinity or zero.

M9.7.4 closes the `aircraft_support_v1` coverage-hardening contract. Single and Monte Carlo run config/report/log payloads declare `m9_7_4_behavior_scope`; behavior-driving fields include `components[].failureDistribution`, top-level `transportPolicies[]`, k-out-of-n, periodic tasks, `basicMissions[].missionPhases`, airports, support activity job DAGs, `supportResources[]` quantities, Monte Carlo sweeps, and seed. The logistics support activity authoring page now reads/writes `scenario.transportPolicies`; legacy `supportActivities[].transportStrategies` rows are migration-only and are not part of clean Project or compiled payloads. `supportOrganization` is approved as governance-only / non-behavior-driving provenance metadata. Root-level `missionPhases` is accepted only as a legacy fallback during Scenario compilation and is not written by clean Project exports. The aircraft-support Monte Carlo sampling contract no longer carries an M9.7.4 pending field list.
