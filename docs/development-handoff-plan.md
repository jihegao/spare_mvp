## 1. 项目背景

“备件规划及任务可靠度验证评估平台”面向装备任务保障场景，目标是通过仿真建模、蒙特卡洛实验和结果分析，支撑备件规划、任务可靠度评估、停机因素归因和保障方案优化。

项目当前已重置路线：之前版本的前端和建模实现均废弃，不再作为本项目当前开发依据。当前先做可评审的前端原型，待前端页面与字段口径稳定后，再改造后端仿真算法、数据适配和输出指标，使其对齐前端字段。

概要设计文档作为历史输入，描述过以下远期平台能力：

1. 备件规划评估模块：围绕任务需求、装备使用、故障产生和备件需求，完成备件需求评估、短板识别和转场携行清单优化。
2. 任务可靠度评估模块：围绕任务需求、装备不可用状态和多波次任务成功判定，完成任务可靠度评估、任务完成度分析和停机因素分析。
3. 系统运行支持模块：面向长周期、大样本蒙特卡洛实验，优化仿真运行效率和样本统计能力。

当前路线 A 不把仓库作为远期平台实现交付，而是把它作为前端 MVP 评审原型交付。该原型只抽取“结果分析”能力，形成 2 个一级模块、4 个结果分析页面，用于演示页面结构、指标表达和评审沟通。

### 2.2 当前形态

当前系统是纯静态前端原型：

1. 无后端服务。
2. 无真实仿真计算。
3. 无接口请求。
4. 无数据持久化。
5. 页面数据以内置常量方式写在 `front/app.js` 中。
6. “启动”按钮仅记录最近启动时间并显示模拟提示。

因此，当前 MVP 的主要价值是验证信息架构、页面表达和演示路径，而不是验证仿真算法或真实业务计算结果。

## 5. 路线 A 已固化口径

当前 `docs/prd.md` 已按 `front/app.js` 的评审演示实现统一口径。转场携行清单不再作为待决策差异处理。

| 项目 | 路线 A 固化口径 | 说明 |
| --- | --- | --- |
| 转场携行清单约束项 | 优化条件 + 任务可靠度 + 备件满足率 + 备件利用率 | 与 `front/app.js` 当前页面一致 |
| 约束输入形式 | 80%、85%、90%、100% 的滚轮阈值 | 当前为演示原型交互，不是正式系统接口契约 |
| 默认值 | 任务可靠度 90%、备件满足率 90%、备件利用率 80% | 与 `state` 默认值一致 |
| 携行数量变化 | 当前随任务可靠度阈值变化 | 备件满足率和备件利用率在本轮作为演示约束展示，不参与真实优化计算 |

后续正式系统是否改为连续数值输入、多目标权重或真实优化计算，应进入接口与数据契约阶段另行确认。

## 6. 后续详细设计边界

当前依据只能形成交接计划和细化方向，暂不建议直接写成完整详细设计。原因如下：

1. 概要设计说明的是远期平台能力，但当前仓库只实现结果分析静态前端。
2. 当前没有后端接口、数据字典、仿真服务协议或数据库结构。
3. 当前结果数据是演示常量，不能反推真实算法输入输出契约。
4. 当前 `core/` 仿真内核尚未和前端结果页面建立验收链路。
5. 正式系统仍需另行确认是优先字段契约和后端算法对齐，还是补充更完整的平台能力。

因此，下一阶段文档应先拆成“前端详细设计”和“前端字段契约”，等字段、接口和真实计算边界确认后，再进入远期平台设计补全。

## 7. 开发协作规则

项目按阶段推进，每个阶段应有明确范围、验收检查、独立分支、提交和 GitHub PR。除初始化仓库外，阶段成果不直接推送到 `main`。

实现阶段采用 TDD：

1. 涉及生产代码、仿真算法、数据适配或前端行为变更时，先写或更新失败测试。
2. 确认测试按预期失败后，再实现最小变更。
3. 变更后运行聚焦测试和相关检查，再提交。
4. 文档阶段不强行创建代码测试，但必须用可重复的搜索、表格检查或链接检查验证口径一致。

允许使用 subagent 做边界清晰的并行工作。只读扫描、文案审阅、验收清单复核等任务可使用降级模型；最终集成、验证、提交、推送和 PR 创建由主 agent 负责。

## 8. 建议细化计划

### 阶段 1：当前 MVP 基线固化

目标：把当前静态原型的范围、页面和验收口径固定下来，避免后续需求讨论混淆远期平台能力与当前 MVP。

建议任务：

1. 对齐 `docs/prd.md` 与 `front/app.js` 的差异。
2. 明确 4 个页面的字段口径、状态阈值和模拟数据来源。
3. 补充一份页面级验收清单。
4. 明确当前 MVP 不包含真实计算、接口请求和数据持久化。

输出物：

1. 更新版 PRD。
2. 页面验收清单 `docs/mvp-acceptance-checklist.md`。
3. 当前 MVP 运行说明。

### 阶段 2：前端详细设计

目标：为后续开发者提供可维护的前端结构设计。

建议任务：

1. 拆分页面配置、模拟数据、渲染组件和交互逻辑。
2. 定义模块、页面、指标卡、表格、图表、状态标签的数据结构。
3. 明确路由规则、页面状态、空数据状态、异常状态和启动反馈。
4. 明确响应式断点和浏览器兼容要求。

输出物：

1. 前端详细设计文档。
2. 页面数据模型说明。
3. 组件拆分建议。

### 阶段 3：前端字段契约

目标：把 4 个前端结果分析页面需要的字段、类型、口径和示例数据固定下来，作为后端仿真算法对齐的输入。

建议任务：

1. 定义四个结果分析页面的字段清单和指标口径。
2. 标注字段来源：前端演示常量、后端可计算指标、规则映射指标或待确认指标。
3. 定义页面字段到后端聚合输出的命名映射。
4. 区分“单次仿真结果”“蒙特卡洛统计结果”和“评审演示字段”。

后续接口方向可以基于字段契约演进：

| 接口 | 用途 |
| --- | --- |
| `GET /api/projects/{projectId}/analysis/spare-shortfall` | 获取备件短板分析结果 |
| `POST /api/projects/{projectId}/analysis/carry-list/run` | 启动转场携行清单优化 |
| `GET /api/projects/{projectId}/analysis/carry-list` | 获取转场携行清单结果 |
| `GET /api/projects/{projectId}/analysis/mission-completion` | 获取任务完成度评估结果 |
| `GET /api/projects/{projectId}/analysis/downtime-factors` | 获取停机因素分析结果 |
| `GET /api/analysis-runs/{runId}` | 查询分析运行状态 |

输出物：

1. 前端字段契约文档。
2. 页面字段到后端输出字段映射表。
3. 演示字段、可计算字段和待确认字段清单。

### 阶段 4：后端仿真算法对齐

目标：在前端字段稳定后，改造 `core/` 仿真算法、数据适配和结果汇总，使后端输出能够支撑前端四个结果分析页面。

建议任务：

1. 从前端页面抽取字段契约和指标口径。
2. 为 `core/` 增加字段级验收测试，先覆盖数据加载、单次仿真输出和页面结果映射。
3. 改造或新增仿真结果聚合层，输出备件短板、转场携行清单、任务完成度和停机因素所需字段。
4. 明确哪些指标来自真实仿真，哪些仍是演示或规则映射。

输出物：

1. 后端字段契约测试。
2. 仿真结果聚合模块。
3. 前后端字段映射文档。

### 阶段 5：远期平台设计补全

目标：在前端原型、字段契约和后端仿真算法对齐后，再参考概要设计历史输入，补齐更完整的平台级设计。

建议任务：

1. 梳理仿真建模数据对象：任务、装备、产品、保障组织、备件、保障人员、保障设备、保障活动。
2. 梳理实验方案对象：实验想定、参数配置、样本数、运行状态、结果数据集。
3. 梳理 ABM 仿真实例化边界：JSON 数据到仿真实体的映射。
4. 梳理蒙特卡洛运行调度、样本统计和结果保存机制。
5. 梳理模板、项目、方案三层数据权限。

输出物：

1. 平台级详细设计。
2. 数据模型详细设计。
3. 仿真实验运行设计。
4. 权限与项目数据组织设计。

## 9. 优先级建议

| 优先级 | 事项 | 原因 |
| --- | --- | --- |
| P0 | 统一 PRD 与当前代码差异 | 避免评审和开发按不同口径理解转场携行清单 |
| P0 | 写明当前 MVP 是静态原型 | 避免把演示数据误解为真实仿真结果 |
| P0 | 写明旧版前端和建模均已废弃 | 避免后续 agent 或开发者继续沿用旧实现 |
| P1 | 抽象前端数据结构 | 为后续接接口和拆组件做准备 |
| P1 | 定义四个页面的字段契约 | 让后端仿真算法知道需要输出什么 |
| P2 | 补充远期平台详细设计 | 依赖前端字段、后端算法和数据存储边界进一步明确 |

## 10. 待确认问题

1. 路线 A 之后是否继续完善前端原型，还是进入后端仿真算法字段对齐。
2. 正式系统中转场携行清单是否仍保留“任务可靠度”作为约束项。
3. 正式系统约束输入采用连续数值输入、多目标权重，还是沿用离散阈值选择。
4. 四个结果分析页面是否都需要支持“实验方案选择”和“历史结果切换”。
5. 后续是否需要补齐仿真建模、实验方案管理和蒙特卡洛运行配置页面。
6. 当前演示数据是否需要替换为来自概要设计或真实样例的标准数据集。

## 11. 下一步建议

建议下一步先执行“阶段 1：当前 MVP 基线固化”。完成后再进入前端详细设计。

最小可执行工作包如下：

1. 更新 `docs/prd.md`，统一转场携行清单的约束项、输入形式和默认值。
2. 新增 `docs/mvp-acceptance-checklist.md`，形成页面级验收清单。
3. 评审前按验收清单检查首页和 4 个分析页，确认页面元素、启动反馈和响应式表现。

完成路线 A 文档收口和验收检查后，再进入前端详细设计；后端仿真算法改造应等待前端字段契约稳定，并以 TDD 方式推进。
