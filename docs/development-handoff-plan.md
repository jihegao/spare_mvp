## 1. 文档定位

本文档是项目总体计划，不再只是一次性交接文档。后续每个阶段的开发、验收、提交和 PR 完成后，都应回写本文件，保持它能回答四个问题：

1. 当前 MVP 的目标和边界是什么。
2. 当前阶段做到哪里，哪些阶段已经完成。
3. 每个阶段的目标、输出物和验收检查是什么。
4. 下一步应该做什么，以及哪些问题仍待确认。

更详细的 PRD、字段契约、验收清单和实现计划可以拆到其他文档；本文档只保留总体路线、阶段状态和跨阶段决策。

## 2. 项目目标和当前 MVP 定义

“备件规划及任务可靠度验证评估平台”面向装备任务保障场景，目标是通过仿真建模、蒙特卡洛实验和结果分析，支撑备件规划、任务可靠度评估、停机因素归因和保障方案优化。

项目路线已经重置：之前版本的前端和建模实现均废弃，不再作为当前开发依据。已有静态前端只能作为页面表达和评审沟通基线，不能定义为当前 MVP。

当前 MVP 是“全部功能的最小实现”，不是“全部功能的完整实现”。它必须覆盖概要设计中的全部 CSCI 部件，并形成最小端到端闭环：

```text
建模输入 -> 实验方案 -> 后端计算或本地服务 -> 结果持久化 -> 前端展示 -> 验收产物
```

当前 MVP 的判定标准：

1. 每个 CSCI 部件至少有一个可访问的前端入口。
2. 每个 CSCI 部件至少有一个后端能力或等价本地服务能力。
3. 每个 CSCI 部件至少有一个可检查的数据对象或运行产物。
4. 每个 CSCI 部件至少有一条可重复的测试或验收检查路径。
5. 结果分析优先由后端运行产物或聚合结果驱动；前端静态常量只能作为空状态、演示状态或测试夹具。

## 4. CSCI 到 MVP 的范围映射

| CSCI 能力 | MVP 最小实现 | 验收重点 |
| --- | --- | --- |
| 仿真建模 | 支持任务、装备、保障组织、备件、保障资源和保障活动的最小项目数据 | 前端可查看或编辑关键字段，后端可保存或导出 JSON |
| 仿真实验方案管理 | 支持从项目数据创建实验方案、编辑最小参数、固定种子启动运行 | 实验方案可被运行记录引用 |
| 可视化推演 | 支持运行启动/停止状态、关键事件日志和基础状态时间线 | 不要求复杂动画，但必须有状态和日志 |
| 蒙特卡洛实验 | 支持小样本批量运行、样本状态记录、基础统计结果和失败样本日志 | 固定种子、小样本、可重复 |
| 备件短板分析 | 输出备件满足率、延误、不满足次数和短板等级 | 前端结果来自聚合结果或结果 JSON |
| 转场携行清单分析 | 输出携行数量建议、约束摘要和指标对比 | 可先使用最小规则或启发式规则 |
| 任务完成度评估 | 输出波次任务成功概率、累计出动架次、可用飞机数和风险状态 | 前端趋势和表格字段与后端契约一致 |
| 停机因素分析 | 输出一级因素、二级因素、观察指标和贡献度统计 | 贡献度口径可检查 |
| 系统运行支持 | 支持运行目录、日志、固定种子、结果 JSON、错误记录和最小批量运行约束 | 运行产物可被人工和测试检查 |

## 6. 阶段工作说明

### Phase 0：静态前端 CSCI 基线

目标：建立当前页面表达基线，覆盖概要设计中的主要 CSCI 入口。

已完成内容：

1. 首页导航覆盖备件规划评估模块、任务可靠度评估模块和系统运行支持模块。
2. 功能入口覆盖建模、实验、备件短板分析、转场携行清单、任务完成度、停机因素和运行管理。
3. 前端测试覆盖页面入口和关键渲染内容。

完成后应保留的证据：

1. 前端测试命令和结果。
2. 涉及的页面和路由清单。
3. 当前静态数据的演示夹具边界。

### Phase 1：MVP 范围与验收契约收口

目标：把当前 MVP 从“静态前端评审原型”统一修正为“覆盖全部 CSCI 部件的前后端最小闭环”，避免后续开发继续围绕旧口径推进。

建议任务：

1. 更新 `docs/prd.md`，把文档主定位升级为全功能最小闭环 MVP PRD。
2. 更新 `docs/mvp-acceptance-checklist.md`，把页面级静态验收升级为前端、后端、仿真运行、结果产物和接口联调验收。
3. 更新 `agent.md`，让后续 agent 以全功能最小闭环作为当前 MVP 口径。
4. 保留静态前端作为 Phase 0 基线，但明确它不是最终 MVP。
5. 用 `rg` 检查旧口径残留，确保“Route A”“静态前端 MVP”等说法不再作为当前目标出现。

阶段输出物：

1. 更新版 PRD。
2. 更新版 MVP 验收清单。
3. 更新版 `agent.md`。
4. 本总体计划的阶段状态更新。

阶段验收检查：

1. 搜索旧口径残留，确认所有保留处都明确标注为历史基线或静态前端基线。
2. 运行前端页面测试。
3. 运行 `python3 -m py_compile core/*.py`，确认候选后端代码仍可导入编译。
4. 检查 Markdown 表格结构。

### Phase 2：MVP 详细设计与字段契约

目标：为前后端一体的最小闭环提供可实现的设计和字段契约。

建议任务：

1. 以 `docs/modeling-json-schema.md` 为输入，先定义建模页如何完整生产 MVP 项目 JSON。
2. 明确两个建模页的创建、编辑、删除、导入、导出、校验、JSON 预览、脏状态、保存状态和错误状态。
3. 将页面可编辑区域映射到 7 类标准对象：`missionProfiles`、`equipmentAssets`、`equipmentTree`、`supportResources`、`inventoryResources`、`supportActivities`、`metricPlans`。
4. 在项目 JSON 边界稳定后，再定义实验方案、运行记录、样本结果、聚合结果和分析结果的数据结构。
5. 定义前端页面、后端 API、`core/` 聚合层和运行产物目录的边界。
6. 明确建模字段、实验字段、运行状态字段和四个结果分析页面字段。
7. 标注字段来源：用户输入、项目数据、实验方案、后端可计算指标、规则映射指标或待确认指标。
8. 区分“真实仿真指标”“最小规则指标”“演示夹具字段”和“待确认字段”。

阶段输出物：

1. MVP 详细设计文档。
2. 建模页完整项目 JSON authoring workflow 文档。
3. 接口与字段契约文档。
4. 运行产物契约文档。
5. 页面字段、API 字段、`core/` 输出字段和结果 JSON 映射表。

阶段验收检查：

1. 建模页功能文档明确用户可以在页面上产生完整项目 JSON，而不是只查看静态字段。
2. 每个前端页面都有字段来源说明。
3. 每个 API 或服务能力都有输入、输出和错误状态说明。
4. 每个结果 JSON 都有示例结构。
5. 每个 CSCI 能力都能追踪到至少一个数据对象和验收路径。

### Phase 3：后端仿真与结果聚合

目标：改造或封装 `core/` 仿真算法、数据适配和结果汇总，使后端输出能够支撑建模、实验运行和四个结果分析页面。

建议任务：

1. 从 MVP 字段契约和概要设计 CSCI 部件抽取最小数据模型。
2. 为 `core/` 增加字段级验收测试，覆盖项目数据加载、实验方案运行、单次仿真输出、蒙特卡洛统计和页面结果映射。
3. 改造或新增仿真结果聚合层，输出备件短板、转场携行清单、任务完成度和停机因素所需字段。
4. 保存运行产物：输入规格、实验配置、运行日志、样本结果、聚合结果、前端结果 JSON。
5. 明确哪些指标来自真实仿真，哪些仍是最小规则或启发式映射。

阶段输出物：

1. 后端字段契约测试。
2. 仿真结果聚合模块。
3. 样例运行产物。
4. 前后端字段映射验证结果。

阶段验收检查：

1. 固定种子运行结果可重复。
2. 聚合结果包含四个结果分析页面所需字段。
3. 运行产物可人工打开检查。
4. 测试覆盖字段契约和最小运行路径。

### Phase 4：本地服务/API 与产物持久化

目标：提供前端和测试可调用的项目、实验、运行、结果查询和产物读取能力。

建议任务：

1. 选择本地 HTTP API、CLI 适配层或两者结合的 MVP 服务形态。
2. 实现项目数据读取和保存能力。
3. 实现实验方案创建、查询和启动运行能力。
4. 实现运行状态、日志和结果产物读取能力。
5. 固定运行产物目录结构和文件命名。

阶段输出物：

1. 本地服务或 CLI 适配层。
2. API 或命令说明。
3. 运行产物目录样例。
4. 服务级测试和烟测命令。

阶段验收检查：

1. 服务可本地启动。
2. 示例项目可创建或加载。
3. 示例实验可启动并写入运行产物。
4. 结果查询能返回前端需要的数据结构。

### Phase 5：前端接入和运行状态闭环

目标：让前端页面结果从后端结果或运行产物驱动，并补齐运行状态、空状态和错误状态。

建议任务：

1. 为前端增加最小数据访问层。
2. 将四个结果分析页面接入后端聚合结果。
3. 为建模、实验和运行管理页面接入项目、方案和运行状态数据。
4. 保留演示夹具作为本地无服务时的显式降级路径。
5. 补齐加载、空数据、错误和运行中状态。

阶段输出物：

1. 前端数据访问层。
2. 接入后端结果的功能页面。
3. 运行状态和错误状态展示。
4. 前端集成测试或浏览器验收截图。

阶段验收检查：

1. 前端页面可以展示后端产物结果。
2. 后端不可用时的降级提示清楚，不伪装成真实结果。
3. 结果字段和 Phase 2 契约一致。
4. 桌面和移动视口无明显布局破坏。

### Phase 6：MVP 总体验收与发布准备

目标：完成全功能最小闭环验收，形成可审查、可复现、可交付的 MVP 证据。

建议任务：

1. 执行端到端验收：建模输入、实验运行、后端计算、产物持久化、前端展示。
2. 更新 `docs/mvp-acceptance-checklist.md` 的每一项状态和证据。
3. 更新 `docs/prd.md`、字段契约和总体计划中的已实现边界。
4. 生成或整理样例运行产物。
5. 提交、推送并创建阶段 PR。

阶段输出物：

1. 完整验收清单。
2. 测试和烟测输出。
3. 样例运行产物。
4. 阶段 PR。

阶段验收检查：

1. 所有 P0 验收项完成。
2. 样例运行可重复。
3. 文档没有把演示夹具误称为真实仿真结果。
4. PR 描述包含范围、验证命令、产物路径和遗留问题。

### Phase 7：远期平台设计补全

目标：在 MVP 最小闭环稳定后，再参考概要设计历史输入，补齐更完整的平台级设计。

建议任务：

1. 梳理完整仿真建模数据对象。
2. 梳理完整实验方案对象和运行调度能力。
3. 梳理 ABM 仿真实例化边界。
4. 梳理长周期蒙特卡洛运行、样本统计和结果保存机制。
5. 梳理项目、模板、方案、用户权限和协作能力。

阶段说明：Phase 7 不阻塞当前 MVP。只有当前端、后端、仿真、产物和验收闭环稳定后，才进入远期平台补全。

## 7. 每阶段完成后的更新要求

每个阶段完成后，必须在同一个 PR 或后续收尾 PR 中更新本文档。更新内容至少包括：

1. 将阶段状态从“未开始”或“进行中”改为“已完成”。
2. 在对应阶段说明中补充实际完成内容。
3. 写明验证命令、验证结果和关键产物路径。
4. 记录偏离原计划的范围变更。
5. 将遗留问题移动到“待确认问题”或下一阶段任务。
6. 更新“当前阶段”和“当前执行状态与后续 PR 队列”。
7. 如果创建了 PR，补充 PR 编号或链接。

## 8. 开发协作规则

项目按阶段推进，每个阶段应有明确范围、验收检查、独立分支、提交和 GitHub PR。除初始化仓库外，阶段成果不直接推送到 `main`。

实现阶段采用 TDD：

1. 涉及生产代码、仿真算法、数据适配或前端行为变更时，先写或更新失败测试。
2. 确认测试按预期失败后，再实现最小变更。
3. 变更后运行聚焦测试和相关检查，再提交。
4. 文档阶段不强行创建代码测试，但必须用可重复的搜索、表格检查或链接检查验证口径一致。

允许使用 subagent 做边界清晰的并行工作。只读扫描、文案审阅、验收清单复核等任务可使用降级模型；最终集成、验证、提交、推送和 PR 创建由主 agent 负责。
