## 1. 项目背景

“备件规划及任务可靠度验证评估平台”面向装备任务保障场景，目标是通过仿真建模、蒙特卡洛实验和结果分析，支撑备件规划、任务可靠度评估、停机因素归因和保障方案优化。

项目当前已重置路线：之前版本的前端和建模实现均废弃，不再作为本项目当前开发依据。已有静态前端只能作为页面表达和评审沟通基线，不能再定义为当前 MVP。当前 MVP 应定义为覆盖概要设计全部 CSCI 部件的全功能最小闭环：前端页面、后端接口、仿真数据适配、最小仿真实验运行、结果汇总、运行产物和验收测试都需要形成可运行链路。

概要设计文档作为历史输入，描述过以下远期平台能力：

1. 备件规划评估模块：围绕任务需求、装备使用、故障产生和备件需求，完成备件需求评估、短板识别和转场携行清单优化。
2. 任务可靠度评估模块：围绕任务需求、装备不可用状态和多波次任务成功判定，完成任务可靠度评估、任务完成度分析和停机因素分析。
3. 系统运行支持模块：面向长周期、大样本蒙特卡洛实验，优化仿真运行效率和样本统计能力。

当前 MVP 不等同于远期完整版平台，但也不应只是前端静态原型。它应在所有 CSCI 部件上各实现一条最小可用路径，允许功能深度、模型精度、数据规模和运行调度能力保持简化，但必须证明“建模输入 -> 实验运行 -> 后端计算 -> 结果持久化 -> 前端展示 -> 验收产物”的端到端链路成立。

### 2.2 当前形态

当前已完成形态是纯静态前端原型：

1. 无后端服务。
2. 无真实仿真计算。
3. 无接口请求。
4. 无数据持久化。
5. 页面数据以内置常量方式写在 `front/app.js` 中。
6. “启动”按钮仅记录最近启动时间并显示模拟提示。

因此，当前代码状态只能视为 MVP 前置基线，主要价值是验证信息架构、页面表达和演示路径；它尚未达到当前 MVP 标准。当前 MVP 需要继续补齐后端服务、仿真计算、数据持久化、接口请求、运行状态和前后端字段契约。

### 2.3 当前 MVP 定义

当前 MVP 是“全部功能的最小实现”，不是“全部功能的完整实现”。判定标准如下：

1. 每个 CSCI 部件至少有一个可访问的前端入口、一个后端能力或本地服务能力、一个可验收的数据对象，以及一条可重复的测试或检查路径。
2. 备件规划评估模块、任务可靠度评估模块和系统运行支持模块均进入 MVP 范围。
3. 仿真建模可先支持最小模板、项目和方案数据，不要求完整复杂编辑器。
4. 仿真实验可先支持单一示例项目和固定种子运行，不要求复杂调度和多租户。
5. 蒙特卡洛实验可先支持小样本批量运行、固定样本数和基础统计，不要求长周期大规模性能优化。
6. 结果分析必须由后端运行产物或聚合结果驱动，前端静态常量只能作为空状态、演示状态或测试夹具。
7. 运行产物必须可检查，包括输入规格、运行配置、日志、结果 JSON、指标汇总和前端可展示的数据。

## 5. 当前 MVP 已固化口径

当前 `docs/prd.md` 已补充概要设计 CSCI 部件范围。后续应继续把 PRD 从“前端原型 PRD”升级为“全功能最小闭环 MVP PRD”，并以本交接计划中的当前 MVP 定义为准。转场携行清单的页面交互口径可沿用现有前端，但结果来源必须从静态常量升级为后端聚合输出。

| 项目 | 当前 MVP 口径 | 说明 |
| --- | --- | --- |
| MVP 范围 | 覆盖全部 CSCI 部件 | 每个部件做最小实现，不做完整远期平台 |
| 前端范围 | 不止 4 个结果页 | 还需补齐建模、实验、运行状态和产物检查入口 |
| 后端范围 | 必须纳入 MVP | 提供项目数据、实验方案、运行、结果查询和产物读取能力 |
| 仿真范围 | 最小可运行仿真闭环 | 支持固定种子、小样本、示例项目和基础统计 |
| 结果来源 | 后端运行产物优先 | 静态常量只能作为兜底、演示或测试夹具 |
| 转场携行清单约束项 | 优化条件 + 任务可靠度 + 备件满足率 + 备件利用率 | 可沿用 `front/app.js` 当前页面交互 |
| 约束输入形式 | 80%、85%、90%、100% 的滚轮阈值 | 当前 MVP 可继续使用离散阈值，正式系统再评估连续输入或多目标权重 |
| 携行数量变化 | 由后端最小优化规则或启发式规则输出 | 不再只由前端静态映射决定 |

后续正式系统是否改为连续数值输入、多目标权重或更复杂优化计算，应进入详细设计阶段另行确认；当前 MVP 先保证前后端闭环和产物可验收。

## 6. 后续详细设计边界

当前依据可以形成 MVP 全功能最小闭环的开发计划，但仍不应直接承诺远期完整版详细设计。原因如下：

1. 概要设计说明的是远期平台能力，当前 MVP 只做全部功能的最小闭环，不做完整能力深度。
2. 当前没有稳定后端接口、数据字典、仿真服务协议或数据库结构，需要在 MVP 阶段补齐最小版本。
3. 当前结果数据是演示常量，不能反推真实算法输入输出契约，需要以后端产物为准重新定义字段契约。
4. 当前 `core/` 仿真内核尚未和前端结果页面建立验收链路，需要纳入 MVP 开发主线。
5. 正式系统仍需另行确认复杂建模编辑器、长周期调度、权限体系和高精度算法实现边界。

因此，下一阶段文档应先拆成“MVP 详细设计”“接口与字段契约”“运行产物契约”和“验收清单”，等最小闭环稳定后，再进入远期平台设计补全。

## 7. 开发协作规则

项目按阶段推进，每个阶段应有明确范围、验收检查、独立分支、提交和 GitHub PR。除初始化仓库外，阶段成果不直接推送到 `main`。

实现阶段采用 TDD：

1. 涉及生产代码、仿真算法、数据适配或前端行为变更时，先写或更新失败测试。
2. 确认测试按预期失败后，再实现最小变更。
3. 变更后运行聚焦测试和相关检查，再提交。
4. 文档阶段不强行创建代码测试，但必须用可重复的搜索、表格检查或链接检查验证口径一致。

允许使用 subagent 做边界清晰的并行工作。只读扫描、文案审阅、验收清单复核等任务可使用降级模型；最终集成、验证、提交、推送和 PR 创建由主 agent 负责。

## 8. 建议细化计划

### 阶段 1：当前 MVP 范围重定义

目标：把当前 MVP 从“静态前端原型”重定义为“覆盖全部 CSCI 部件的前后端最小闭环”，避免后续需求讨论继续把 4 个结果页误认为 MVP 全量范围。

建议任务：

1. 将 `docs/prd.md` 升级为全功能最小闭环 MVP PRD。
2. 将 `docs/mvp-acceptance-checklist.md` 从页面级静态验收升级为前后端闭环验收。
3. 明确 CSCI 全部部件在 MVP 中的最小实现形态。
4. 明确已有静态前端是基线，不是最终 MVP。

输出物：

1. 更新版 PRD。
2. 全功能 MVP 验收清单 `docs/mvp-acceptance-checklist.md`。
3. 当前 MVP 运行与产物说明。

### 阶段 2：MVP 详细设计

目标：为后续开发者提供前后端一体的最小闭环设计。

建议任务：

1. 定义项目数据、实验方案、运行记录、样本结果和分析结果的数据结构。
2. 定义前端页面、后端 API、`core/` 聚合层和运行产物目录的边界。
3. 明确路由规则、页面状态、空数据状态、异常状态、启动反馈和运行进度。
4. 明确响应式断点、浏览器兼容要求和本地服务启动方式。

输出物：

1. MVP 详细设计文档。
2. 前后端数据模型说明。
3. 页面、接口和产物目录拆分建议。

### 阶段 3：接口与字段契约

目标：把前端页面、后端 API、仿真内核和运行产物之间的字段、类型、口径和示例数据固定下来。

前置输入：先以 `docs/modeling-detailed-requirements.md` 固化两类建模页面的字段、业务规则、校验规则和验收标准，再拆解 API、JSON Schema、前端表单和 `core/` 适配任务。

建议任务：

1. 定义建模、实验、运行状态和四个结果分析页面的字段清单和指标口径。
2. 标注字段来源：用户输入、项目数据、实验方案、后端可计算指标、规则映射指标或待确认指标。
3. 定义页面字段到后端 API、`core/` 聚合输出和结果 JSON 的命名映射。
4. 区分“项目数据”“实验方案”“单次仿真结果”“蒙特卡洛统计结果”和“前端展示字段”。

后续接口方向可以基于字段契约演进：

| 接口 | 用途 |

输出物：

1. 接口与字段契约文档。
2. 页面字段、API 字段、`core/` 输出字段和结果 JSON 映射表。
3. 用户输入字段、可计算字段、规则映射字段和待确认字段清单。

### 阶段 4：后端仿真与产物闭环

目标：改造 `core/` 仿真算法、数据适配和结果汇总，使后端输出能够支撑建模、实验运行和四个结果分析页面。

建议任务：

1. 从 MVP 字段契约和概要设计 CSCI 部件抽取最小数据模型。
2. 为 `core/` 增加字段级验收测试，覆盖项目数据加载、实验方案运行、单次仿真输出、蒙特卡洛统计和页面结果映射。
3. 改造或新增仿真结果聚合层，输出备件短板、转场携行清单、任务完成度和停机因素所需字段。
4. 保存运行产物：输入规格、实验配置、运行日志、样本结果、聚合结果、前端结果 JSON。
5. 明确哪些指标来自真实仿真，哪些仍是最小规则或启发式映射。

输出物：

1. 后端字段契约测试。
2. 仿真结果聚合模块。
3. 运行产物目录和示例结果。
4. 前后端字段映射文档。

### 阶段 5：远期平台设计补全

目标：在前端原型、字段契约和后端仿真算法对齐后，再参考概要设计历史输入，补齐更完整的平台级设计。

建议任务：

1. 梳理仿真建模数据对象：任务、装备、产品、保障组织、备件、保障人员、保障设备、保障活动。
2. 梳理实验方案对象：实验想定、参数配置、样本数、运行状态、结果数据集。
3. 梳理 ABM 仿真实例化边界：JSON 数据到仿真实体的映射。
4. 梳理蒙特卡洛运行调度、样本统计和结果保存机制。
5. 梳理模板、项目、方案三层数据权限。

输出物：

1. 平台级详细设计。
2. 数据模型详细设计。
3. 仿真实验运行设计。
4. 权限与项目数据组织设计。

## 9. 优先级建议

| 优先级 | 事项 | 原因 |
| --- | --- | --- |
| P0 | 将 PRD 升级为全功能最小闭环 MVP PRD | 避免继续把 4 个静态结果页误认为当前 MVP |
| P0 | 将验收清单升级为前后端闭环验收 | 避免只验收页面元素而漏掉后端、仿真、产物和接口 |
| P0 | 写明已有静态前端只是 MVP 前置基线 | 避免把演示数据误解为真实仿真结果 |
| P0 | 写明旧版前端和建模均已废弃 | 避免后续 agent 或开发者继续沿用旧实现 |
| P1 | 定义 MVP 接口与字段契约 | 让前端、后端和 `core/` 共享同一套数据口径 |
| P1 | 补齐后端 API 和运行产物契约 | 让建模、实验运行、结果查询和产物检查可验收 |
| P1 | 改造 `core/` 结果聚合层 | 让四个结果分析页面由后端产物驱动 |
| P2 | 补充远期平台详细设计 | 在 MVP 最小闭环稳定后再扩展完整平台能力 |

## 10. 待确认问题

1. 当前 MVP 的最小项目数据是否以概要设计中的任务、装备、保障组织、备件、保障活动为第一版字段边界。
2. 后端采用本地 HTTP API、CLI 适配层，还是两者同时提供。
3. MVP 阶段是否需要轻量数据库，还是先使用文件型项目数据和运行产物目录。
4. 转场携行清单在 MVP 中采用启发式规则、简化优化算法，还是直接接入现有 `core/` 候选能力。
5. 四个结果分析页面是否都需要支持“实验方案选择”和“历史结果切换”。
6. MVP 验收样例数据是否以概要设计字段、`core/dataset/` 数据，还是人工整理的标准示例项目为准。
7. 系统运行支持模块在 MVP 中的最小并发、样本数和日志粒度要求。

## 11. 下一步建议

阶段 1 已完成，下一步进行 Route A 验收。Route A 验收完成后，再进入 MVP 详细设计和接口字段契约。

最小可执行工作包如下：

1. 更新 `docs/prd.md`，把“前端原型 PRD”升级为“全功能最小闭环 MVP PRD”。
2. 更新 `docs/mvp-acceptance-checklist.md`，把静态页面验收升级为前端、后端、仿真运行、结果产物和接口联调验收。
3. 新增或补充 MVP 接口与字段契约，先固定项目数据、实验方案、运行记录、样本结果和四个结果分析输出。
4. 盘点 `core/` 当前能力，确认哪些指标能真实计算，哪些需要 MVP 阶段用最小规则或启发式映射补齐。
5. 设计运行产物目录，明确输入规格、实验配置、日志、样本结果、聚合结果和前端结果 JSON 的文件名与结构。

完成 MVP 范围和契约收口后，即可按 TDD 推进后端仿真、API、前端接入和验收闭环；不再把后端仿真算法改造推迟到静态前端之后。
