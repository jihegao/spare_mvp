# 四级功能页面化前端设计规格

日期：2026-06-17

## 背景

当前前端已经覆盖备件规划、任务可靠度、仿真实验和结果分析的核心概念，但页面组织仍偏向 6 个大视图：建模中心、可靠性框图、保障甘特、可视化仿真、蒙特卡洛、结果分析。这个结构适合原型演示，不适合承载 `docs/3概要设计方案.md` 中明确列出的 2 个一级功能、6 个二级功能、16 个三级功能和四级功能清单。

本规格将前端从“大页摘要”调整为“四级功能独立页面”：一级、二级、三级承担导航归属，四级功能承担主内容视图。每个四级功能页面都要有明确的数据对象、输入编辑区、可视化或表格视图、校验状态、输出或联动摘要。

## 目标

1. 按概要设计表 2 的四级功能清单完整展开页面结构。
2. 每个四级功能拥有独立页面视图和可导航地址。
3. 通过页面模板复用降低实现重复，而不是为每个四级页面手写一套实现。
4. 在页面右侧使用局部 ontology 上下文图，解释当前功能在全局模型中的位置和上下游关系。
5. 保持当前静态前端和本地仿真原型边界，不在本次设计中引入后端、权限系统或真实长任务调度。

## 非目标

1. 不实现完整 Web 平台、用户权限、模板/项目/方案数据权限。
2. 不把小样本原型结果表述为工程级最优方案。
3. 不在本设计阶段修改 Mesa 模型规则或实验算法。
4. 不把全部四级页面都做成完全不同的定制实现。

## 推荐方案

采用“A + C”方案：

- 信息架构采用严格四级功能页矩阵：一级模块、二级功能、三级分组、四级页面。
- 工程实现采用模板化页面系统：用功能清单配置驱动四级页面，复用字段表单、关系图、状态机、可靠性框图、甘特、结果表、指标条、校验面板等组件。

这样用户看到的是完整的功能页体系，工程上仍能保持可维护性。

## 信息架构

页面结构采用四层：

1. 一级功能：`备件规划评估模块`、`任务可靠度评估模块`。
2. 二级功能：`仿真建模`、`仿真实验`、`结果分析`。
3. 三级功能：例如 `任务建模`、`装备建模`、`保障组织建模`、`保障活动建模`。
4. 四级功能：真正可进入的页面视图。

左侧导航保留完整层级。一级模块作为大分区，二级功能作为折叠组，三级功能作为小组标题，四级功能作为可点击页面。主内容区一次只显示一个四级功能页面。

## 页面模板

每个四级页面采用一致骨架：

1. 页面标题区：显示四级功能名称、一级到三级归属路径、当前方案名称。
2. 左侧导航区：显示完整四层功能树，当前四级功能高亮。
3. 主编辑区：承载当前功能的核心输入、图形、表格或控制面板。
4. 校验区：显示字段缺失、关系端点、参数范围、场景一致性等问题。
5. 输出/联动摘要：说明当前页面写入哪些数据对象，以及会影响哪些实验或分析页面。
6. 右侧 ontology 上下文区：用局部 ontology 图表达当前页面在全局模型中的位置。

### 主编辑区类型

| 功能类型 | 主编辑组件 |
| --- | --- |
| 任务建模 | 表单、任务层级树、任务阶段状态机 |
| 装备建模 | 装备组成树、故障参数表、可靠性框图 |
| 保障组织建模 | 保障组织树、库存表、人员/设备能力表 |
| 保障活动建模 | 活动流程表、资源需求组、甘特预览 |
| 仿真实验方案 | 参数表、方案摘要、运行前校验 |
| 可视化推演 | 运行控制、场景视图、事件流、指标条 |
| 蒙特卡洛实验 | 扫参配置、样本摘要、结果表 |
| 结果分析 | 排名表、指标分解、因素贡献图 |

## Ontology 上下文图

右侧上下文区统一使用“局部 ontology 图 + 关系说明”。它不是主编辑画布，而是上下文解释器。

每个页面的 ontology 上下文图至少显示：

1. 当前四级功能节点。
2. 当前页面写入的数据对象，例如 `missionProfile`、`equipment`、`supportNodes`、`reliabilityBlockDiagram`。
3. 上游依赖页面或对象，例如装备可靠性框图依赖装备组成和装备故障。
4. 下游实验、分析或指标，例如任务可靠度评估、停机因素分析、备件短板分析。
5. 当前页面负责的校验关系，例如端点完整、连接类型合法、库存非负、任务阶段可达。

关系标签使用固定语义：

| 关系标签 | 含义 |
| --- | --- |
| `depends_on` | 当前页面依赖的上游对象或页面 |
| `writes_to` | 当前页面写入的场景数据对象 |
| `drives` | 当前页面影响的实验、分析或指标 |
| `validates` | 当前页面负责检查的约束 |
| `shares_with` | 两个一级模块共享的建模数据 |

示例：`装备可靠性框图建模`

```text
装备组成建模 depends_on 装备可靠性框图建模
装备故障建模 depends_on 装备可靠性框图建模
装备可靠性框图建模 writes_to reliabilityBlockDiagram
装备可靠性框图建模 drives 任务可靠度评估
装备可靠性框图建模 drives 停机因素分析
装备可靠性框图建模 validates 端点完整、连接类型、故障参数
```

## 数据流

页面仍围绕单一前端场景状态工作。四级页面不复制私有状态，而是读写同一个 scenario/project JSON。

1. 导航选择四级功能。
2. 页面配置读取当前 scenario 对应数据对象。
3. 用户编辑字段、关系、表格或图节点。
4. 页面即时更新共享 scenario。
5. 页面校验器运行并返回问题列表。
6. 相关页面通过共享数据看到同一结果。
7. 运行单次仿真或蒙特卡洛时，从共享 scenario 生成实验输入。

这延续当前前端原型的约束：所有页面消费同一份项目状态，跨页面切换后编辑结果仍可见。

## 错误处理

1. 缺失字段：在校验区显示字段路径和中文说明。
2. 关系端点缺失：在 ontology 上下文图和校验区同时标记问题对象。
3. 参数超出范围：阻止保存该字段并提示允许范围。
4. 页面没有专属数据时：显示空状态和可创建入口，不降级成空白页。
5. 仿真输入不完整：实验页面显示阻塞原因，不启动运行。
6. 前端脚本加载失败：保留现有可见错误兜底，避免停留在静默加载状态。

## 实现边界建议

后续实现可拆为三层：

1. `feature-catalog`：声明表 2 列出的四级页面、归属路径、数据对象、组件类型和 ontology 上下文关系。
2. `feature-router`：根据当前功能 ID 渲染页面，并维护导航高亮。
3. `feature-page-template`：渲染标题、主编辑区、校验区、输出摘要和 ontology 上下文图。

现有 `front/app.js` 已经过长，实际实现时应优先拆分配置和渲染模块，避免继续把全部四级页面逻辑堆入单文件。

## 验收标准

1. 前端导航可访问所有列入清单的四级页面。
2. 每个四级页面都有独立标题、归属路径和当前页面高亮。
3. 每个页面右侧都有 ontology 上下文图，不再只是文字卡片。
4. 页面清单由集中配置驱动，测试能验证页面数量、功能 ID 唯一性和导航可达性。
5. 共享 scenario 数据在相关页面之间保持一致。
6. 关键页面至少覆盖当前原型已有能力：任务建模、装备故障、可靠性框图、保障活动甘特、单次仿真、蒙特卡洛、结果分析。
7. `npm test` 通过，并新增或更新前端结构测试覆盖四级页面目录和 ontology 上下文图。
